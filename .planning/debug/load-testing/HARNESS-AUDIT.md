# Harness Audit — Phase 8A Burst vs Sustained Reality

**Date:** September 2026  
**Auditors:** Engineering & Load Testing Team  
**Scope:** In-depth technical audit of `.planning/debug/load-testing/` and `tests/load/`

---

## 1. Executive Finding: The 250-User Threshold is a Connection-Pool Semaphore Artifact

The initial Phase 8 report reported:
- 250 concurrent users: 0% errors (7,416.78 RPS, P95: 38.20ms)
- 275 concurrent users: 5.02% errors (HTTP 503)
- 300 concurrent users: 12.76% errors
- 500 concurrent users: 33.11% errors

Our code inspection confirms: **The 250–275 failure boundary was NOT an application capacity ceiling. It was a direct artifact of how Phase 8A was scripted.**

Specifically:
1. `tests/load/local-backend.ts` explicitly defined:
   ```typescript
   this.maxConcurrentConnections = options.maxConcurrentConnections ?? 250;
   ...
   if (this.activeConnections > this.maxConcurrentConnections) {
     this.activeConnections--;
     res.writeHead(503, { "Content-Type": "application/json" });
     res.end(JSON.stringify({ error: "Server connection pool exhausted (HTTP 503)" }));
     return;
   }
   ```
2. In `tests/load/run-phase8-benchmark.ts`, all $N$ simulated users were dispatched inside an un-throttled `Promise.all`:
   ```typescript
   const sessionPromises = userProfiles.map((p) =>
     executeUserSession(p, backend.baseUrl, apiKey)
   );
   const sessionResults = await Promise.all(sessionPromises);
   ```
3. Each simulated user fired all 5–7 API calls in immediate sequential microsecond succession without any human think time, pause, or typing simulation.
4. As a result, the entire 250-user stage executed in **0.196 seconds** (1,450 HTTP requests in 196ms = **7,416.78 requests/second**).
5. At 275 users, 275 concurrent HTTP requests arrived at the exact same millisecond. Since the server had `maxConcurrentConnections = 250`, exactly 25 requests were immediately shed with HTTP 503.

**Conclusion:** Phase 8A did not measure 250 concurrent *users*. It measured a **7,400+ RPS instantaneous burst attack** saturating a 250-socket concurrency gate.

## 2. Answers to the 14 Audit Questions

| # | Question | Finding & Evidence |
| :--- | :--- | :--- |
| **1** | What represents a "user"? | In Phase 8A, a "user" was a single async promise executing 5 to 7 HTTP requests in a zero-delay loop (`auth/v1/user` $\to$ `projects` list $\to$ `projects` create $\to$ `projects` patch $\to$ `projects` select). |
| **2** | Is each user a real authenticated session? | Yes. Each user presented an isolated `Authorization: Bearer test_token_<userId>` header. |
| **3** | Is each session using a real JWT? | In Phase 8A, tokens used the format `test_token_<userId>` parsed by `getUserIdFromToken()`. The remote test verified genuine Supabase GoTrue tokens. |
| **4** | Is token validation actually occurring? | Yes. Every request passed through `getUserIdFromToken(token)`. Missing or malformed tokens returned HTTP 401 (`permission denied for table projects`). |
| **5** | Is the test hitting local Supabase or remote Supabase? | Phase 8A ran against `http://127.0.0.1:54321` (high-fidelity local PostgREST/GoTrue engine) after verifying that the live remote Supabase project rejected dynamic signups with `email rate limit exceeded`. |
| **6** | Are requests going directly to PostgREST? | Yes. Exact PostgREST REST paths (`/rest/v1/projects`, `/rest/v1/profiles`, `/rest/v1/rpc/record_usage`) and GoTrue paths (`/auth/v1/user`) were invoked. |
| **7** | Are connections persistent? | No. Standard Node.js `fetch` without an explicit HTTP Agent pool opened and closed sockets per request burst. |
| **8** | Are HTTP keep-alive connections being reused? | Keep-alive was default, but because requests were fired in parallel bursts across new user contexts, socket reuse was minimal. |
| **9** | How many requests does each simulated user generate? | 5 requests for Light workload, 6 for Normal, 7 for Heavy. |
| **10** | How long does each simulated user remain active? | **Only 90ms to 240ms total!** Users terminated as soon as their 5–7 requests completed. |
| **11** | Does the test simulate human think/edit time? | **NO.** Zero delay between edits or saves. |
| **12** | Is the measured RPS generated artificially by the harness? | **YES.** 7,416 RPS was generated by compressing hundreds of user workflows into 196ms. In real life, 250 users generating 1 save every 60s would produce ~4.1 RPS. |
| **13** | Is the connection pool being saturated because the test creates too many simultaneous sockets? | **YES.** 275 simultaneous sockets hit a hard ceiling of 250 concurrent connections at the same instant. |
| **14** | Is the test measuring application capacity or merely backend connection capacity? | It measured **instantaneous backend socket saturation**, NOT realistic HandText active-user capacity. |

## 3. The Real-World User Model for Phase 8B

In real life, HandText document editing has an asymmetric persistence pattern:

```
[User Action]                [Network PostgREST Requests]    [Client Operations]
-----------------------------------------------------------------------------------------
Typing text, words, symbols   0 requests                      Local IndexedDB (3000ms debounce)
Inserting Math / Tables       0 requests                      Local DOM & Canvas render
Switching Tabs                0 requests                      Client-side React Router
Explicit Cloud Save (Ctrl+S)  1 request (PATCH)               Cloud sync (every 30–120s)
Reloading / Opening Project   1 request (GET)                 Project load (on mount)
Generating Pages              1 request (POST RPC)            Handwriting generation
```

- **Phase 8A Model:** 1 simulated user = ~30 requests/second (continuous saturation).
- **Phase 8B Model:** 1 simulated user = 1 active session sustained over **5 to 10 minutes**, executing typing think-time, client-side IndexedDB persistence, and periodic cloud saves (1 save every 30–90 seconds).
